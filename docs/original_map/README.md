# Original Castle Fight map evidence

This directory keeps original Warcraft III maps used as compatibility evidence and reproducible plaintext extractions of their gameplay/map data. Exact source/extraction revisions are registered in `releases.json`; a map-version label by itself is not a reproducible identity.

The retained 9.27 baseline source is `5329_Castle_Fight_DE_beta9.27_w3p.w3x` (SHA-256 `9e3519bbc2a0fb6145460dd8b5730e9a35b2fd5923d63404eaf31e3618208a88`). It identifies itself as **Castle Fight DE Beta 9.27**, authored by **Frotty**. Its map-info format is 31 and records Warcraft III version `2.0.4.23745`. The committed `extracted/` tree is the working alias for registered revision `9.27/r1`; the manifest also records its immutable Git tree identity so later corrected extractions cannot silently rewrite that historical revision.

The 9.32 source archive is retained separately under `releases/9.32/r1/source.w3x` (SHA-256 `4181d8aecc3bfe15f66fa071d079ea62deda1f663f5e19f5dc34edd7401b738c`). Its internal W3I identifies **Castle Fight DE Beta 9.32**, authored by Frotty, with format 31 and declared Warcraft version `2.0.4.23745`. It is registered as **archived only**: no reviewed 9.32 extraction or native runtime-content compatibility is claimed yet.

Do not edit generated extraction files by hand. Retained extraction destinations are append-only by default. Resolve and verify an exact registered revision with:

```sh
python tools/wc3-map/release_manifest.py list
python tools/wc3-map/release_manifest.py verify 9.27 r1
```

For a registered revision whose extraction status is still pending, run `tools/wc3-map/extract-release.sh <version> <revision>` after preparing the matching Warcraft base-data cache. The underlying extractor refuses to overwrite a non-empty output directory unless `CF_MAP_EXTRACT_OVERWRITE=1` is explicitly set for disposable scratch output. A corrected retained extraction therefore gets a new revision rather than replacing the old one.

See `tools/wc3-map/README.md` for tool provenance, build instructions, archive-protection details, format caveats, and the meaning of each generated file.

- playable area: **100 × 56** tiles;
- pathing/buildability grid: **528 × 256** cells;
- six configured player slots split across two forces, with the three western starts near `x=-4352` and three eastern starts near `x=4352`;
- **1,780** placed doodads/destructables, now joined to inherited names and pathing footprints;
- **585** custom unit/building object definitions plus 28 modified standard units;
- **709** custom abilities plus 14 modified standard abilities;
- **96** custom buffs, **16** custom items, **26** custom destructables, and four custom doodad definitions;
- map-specific gameplay constants from `war3mapMisc.txt`, including damage-type/armor multipliers;
- human-readable names and tooltips describing production rates, health, attacks, armor, spell effects, cooldowns, mana use, special targeting behavior, and legendary mechanics;
- the complete **11.8 MB** W3P-protected runtime Lua plus Lua-aware indexes of **6,879** named function definitions, **5,723** distinct lexical call targets, and **29,478** caller→callee edges;
- **12,611** direct script references covering **1,332** of the map's **1,461** distinct object rawcodes, plus **157** runtime unit/ability mutation call sites; exact named-call propagation links **117** of those mutator sites to **270** rawcodes through **6,728** auditable shortest-path traces;
- a structurally recovered protected-ability runtime table containing **452** cooldown/mana assignments across **259** ability-level rows and **254** abilities, plus **17** explicit JASS-add restores;
- a decoded protected `UnitStat` source table covering **549 unit definitions** with **1,887** explicit runtime overrides across HP, armor/defense, movement speed, and both attacks' base damage/dice/cooldown/range;
- a generated **162-row** building→spawned-unit effective combat catalog containing HP, armor, DPS, attack range, move speed, spawn count, and air-target capability for 162 distinct production units;
- a normalized **324-row** production weapon catalog preserving both attack slots per production unit, including **174 available attack profiles** and the Mountain Giant's one structurally detected conditional War Club profile;
- a normalized **481-link / 291-unique-ability** production-unit ability catalog that applies protected runtime cooldown/mana, preserves labeled ability Data fields and script-reference provenance, and retains inherited Ghost/Locust/Invulnerable definitions;
- **37** exact scripted unit-spell registrations with concrete handler, unit/ability rawcodes, exact target-mode semantics, base order and production-building cross-link where applicable; **35** belong to normal `xO` production units, while Twin Smiley and Mana Generator remain explicit non-production registrations;
- a **167-row** production-unit death/corpse catalog carrying exact Warcraft `Death Type` raise/decay capability bits and per-unit `Death Time`, plus resolved global decay constants (flesh **2 s**, bones **25 s**, structures **0.1 s**);
- a generated **240-building / 15-race** authored building catalog with **167** production definitions, **90** upgrade/precursor edges, exact runtime spawn intervals/costs, recovered race-wrapper income/role/AI/mode semantics, and one explicitly campaign-only Critter race; the 162 normal production rows match the 162-row `xO` catalog exactly;
- **15** exact scripted building-spell registrations cross-linking owning building, ability rawcode and concrete Lua handler; all 15 now also have normalized mechanic rows joining script-proven targeting/delivery/constants to separately sourced linked WC3 effect objects, while unresolved or conflicting evidence remains explicit;
- **3** normalized corpse-dependent building mechanics: Skull Pile and Skull Shrine scripted Raise Dead, plus Vessel of Purity corpse consumption/damage, with exact predicates, cadence, summon probabilities, radii/damage and source handlers retained;
- **57,253** exact named-function alias assignments from Wurst's generated dispatch/prototype tables, including **2,801** structurally self-named slot→implementation mappings, plus **308** named function-value arguments from the generated initialization layer;
- a full inheritance merge against Warcraft III `2.0.4.23745` **Default (TFT)** data (`custom_v1` / `custom,V1`): **148,757** resolved editor-field rows and **185,907** inherited source-table field rows across all 1,487 map object definitions;
- all **207** standard pathing textures decoded to exact 32-world-unit pathing cells, with every unit/building and placed doodad pathing reference resolved;
- normalized static unit/object tables, a decoded protected UnitStat overlay, a separate runtime/effective production-unit combat summary, and **325** building-like definitions with exact footprint masks rather than filename size guesses.

Examples visible directly in the extracted catalogs include Footman, Mortar, Sniper, Faerie Dragon, their production buildings, and legendary/utility buildings such as Shrine of Destruction, Eraser, Snowveil Fountain, and Well of Pain. These tooltips already expose many mechanics that will eventually become compatibility fixtures rather than guessed native behavior.

## Evidence quality

Treat this directory as reverse-engineering evidence, not yet as final native content.

The terrain/pathing/doodad placement files are direct decodes of authoritative map data. The original `catalog/` files remain map-override views. The newer `extracted/resolved/` tree fills inherited fields from the exact installed Warcraft III build and the W3I-selected **Default (TFT)** balance set, which resolves to `custom_v1` / `custom,V1` on this build. `resolved/object-fields.tsv` records base value, all map candidates, last-write value, recovered value, editor metadata, and source table/field so a later importer does not have to infer inheritance again. `resolved/base-data-manifest.json` hashes every ignored local base file used to produce that committed merge.

Physical geometry is likewise explicit now. `resolved/buildings.tsv` contains exact pathing-mask dimensions and cells; `resolved/pathing-textures.json` retains the masks themselves; and `resolved/placed-doodads.tsv` joins all 1,780 placed objects to their inherited pathing texture and object name. Ordinary moving-unit physical size remains represented by the unit collision field rather than a building-style pathing mask.

The W3P object files contain 14 conflicting repeated fields across six objects. These are not hidden: `resolved/protection-conflicts.tsv` preserves every value and the resolution reason. Convenience catalogs recover only the observed numeric `value → 0/1 → 0/1` duplicate-sentinel pattern; ambiguous string changes retain ordinary last-write semantics. This is only one protection mechanism: many spawned-unit fields are poisoned by single map values and therefore cannot be repaired from object-data duplication alone.

The runtime Lua remains the strongest source for custom mechanics implemented in script and for values mutated after map load. It is W3P-obfuscated, so the extraction preserves the original code without executing it and lexes the minified source into exact function spans, caller→callee edges, rawcode reference sites, runtime unit/ability mutator sites, and Wurst's generated function-alias/dispatch assignments. `script/rawcode-mutator-traces.tsv` follows exact calls to named functions and records one deterministic shortest path from direct rawcode evidence to reachable mutator sites. `script/function-aliases.tsv` separately records exact slot assignments; the `slot-name-prefix` classification is only a structural clue that makes concrete-looking generated handlers easy to find, while inherited/alternate assignments are retained as `assigned-other-target`. Neither a call trace nor an alias proves argument flow, branch execution, virtual receiver selection, or callback execution. Conversely, absence of a trace is not proof that a runtime relationship does not exist.

The protected ability-field table is stronger evidence than generic reachability. The generated Lua constructs explicit expected cooldown/mana rows, applies them through `applyProtectedAbilityFields`, and contains verification helpers that compare live Warcraft ability fields against those values. `resolved/protected-ability-fields.tsv` joins all **452** assignments back to static resolved object data; all **452** differ from the static values, which are commonly W3P sentinels such as cooldown `99` and mana `9999`. For example Rescue Strike `A005` resolves statically to `99/9999` but the protected runtime table specifies cooldown **60** and mana **0**; Snowfall `A0HO` specifies **1** and **15**. The extractor preserves both sources rather than silently replacing the static object data.

Unit combat stats have a similarly authoritative protection source. Function `jP` contains **549** encoded `UnitStat` rows. The visible `cP`/`dP` functions completely specify the row decoder, and `UnitStat_applyTo` shows exactly how the resulting fields are written to live units. The extractor therefore recovers **1,887** explicit overrides without running the map VM. `resolved/protected-unit-stats.tsv` overlays those values on the static fallback field-by-field and derives the resulting attack primitives. Faerie Dragon `e000`, for example, becomes HP **460**, armor **2**, attack **49 + 1d1**, cooldown **1.75 s**, range **350**, yielding about **28.57 DPS** instead of the poisoned static HP/range values of `1/1`. Wizard `h00W` reveals a protected **1.8 s** attack cooldown and range **650**.

Function `xO` separately creates one `UnitEffectiveStat` summary row for each of **162** production buildings and **162** unique spawned unit IDs, and `applyEffectiveUnitStat` copies those values into the building catalog. `resolved/effective-unit-stats.tsv` compares that table against both static object data and the decoded UnitStat overlay. With the corrected W3I-selected fallback, the UnitStat layer matches `xO` for **162/162 HP**, **162/162 armor**, **160/162 DPS summaries**, **159/161 comparable attack ranges**, and **162/162 movement speeds**. The two missing DPS comparisons are special/no-normal-base-attack cases. The two range differences are Mountain Giant `e00F` (`xO=277`, weapon ranges `128/150`) and Roterothopter `h06Q` (`xO=999`, weapon ranges `500/500`); both happen to equal `sum(weapon ranges)-1`, a pattern retained as evidence rather than interpreted as a weapon rule. `resolved/production-unit-attacks.tsv` is therefore the preferred import view for per-weapon combat data, while `xO` remains the map's own one-number production/AI summary.

Mountain Giant's tree-club behavior is directly recoverable rather than tooltip-only. `onUnitEnteredMap` routes `e00F` to `castNatureAttackTree`, which creates a temporary `VTlt` tree 32 world units in front of the giant, issues target order ID `852511`, resumes attack behavior after 1.6 seconds, and removes the temporary destructable two seconds later. Its `A0BC` ability inherits Warcraft's `Agra` War Club mechanics and decodes to attack-index switch `0 → 1` with **Maximum Attacks = 10**. The default weapon is normal, 128 range, `124 + 1d51` at 1.8 s; the temporary club weapon is siege, can target air/ground/structures, 150 range, and `174 + 1d26` at 2.2 s. Roterothopter `h06Q` instead has two ordinary enabled 500-range weapons: `19 + 1d11` at 1.0 s against air (**25 DPS**) and `19 + 1d1` at 1.0 s against structures (**20 DPS**).

`resolved/production-unit-abilities.tsv` performs the corresponding import normalization for initial unit abilities. All **481** links resolve across **291** unique rawcodes; **77** links use protected runtime cooldown/mana values instead of their static sentinels, while only six links depend on unmodified Blizzard definitions (`Aeth` Ghost, `Aloc` Locust, `Avul` Invulnerable). Each row retains the initial level, inherited/base ability rawcode, effective cooldown/mana provenance, range/area/targets/buffs, labeled ability-specific Data fields, and direct Lua reference functions/counts. It is an ability-definition inventory, not yet a claim that scripted mechanics have been fully translated.

The scripted subset is now indexed separately. `script/unit-spell-registrations.tsv` reconstructs **37** generated `UnitSpellClosure` registrations by joining closure construction/prototype dispatch to the protected unit/ability/target-mode registry; 36 use the protected five-argument registry and one Mine Layer registration is emitted inline with an expected immediate `MineDummy` (`h09M`). The map's own E2E target matcher gives the target-mode semantics exactly: 20 enemy-ground combat-sapper registrations, 3 enemy-flying, 10 allied-ground, 2 allied-any, 1 allied-structure and 1 immediate-enemy-special-unit. `resolved/unit-spells.tsv` joins those rows to effective protected cooldown/mana, base order strings and production source buildings. Thirty-five are normal production units; Twin Smiley and Mana Generator are retained as the two non-`xO` registrations rather than dropped or forced into the production catalog. Protected order expressions whose encrypted order string cannot be read statically remain marked `protected-order-expression`; the independently resolved ability `base_order` is retained beside them as context, not claimed to be a decryption of that argument.

`script/unit-spell-mechanics.tsv` / `resolved/unit-spell-mechanics.tsv` add a complete implementation-evidence profile for all 37 handlers. They classify the direct primitive (dummy target/point/immediate cast, spawned mover, protected ability application, unit order, scheduled callback, or delegated helper), recover exact generated `doAfter`, `ForGroupCallback` and `CallbackPeriodic` implementations from Wurst prototype assignments, preserve scheduled/random timing literals, index semantic effect-call argument sites and retain numeric literals per spell-specific source function. Bounded exact named-call/dispatch paths retain reachable map objects as evidence rather than assuming every referenced rawcode is an effect. The resolved view joins those objects back to ability/unit data. This now exposes, for example, Sagepaw Monk's `A0GP` Healing Spray, Twin Smiley's delayed `A0FS` Thunder Clap plus 600-radius/100-mana script constants, Flamegunner Sergeant's corresponding 300-radius/100-mana grenade constants, Harpy Witch's 75-life steal constants, Forest Troll Trapper's `A0FC` Ensnare, Mine Layer's 50–220 placement radius and Landmine spawn, and Mana Generator's improvement abilities. Dynamic callbacks are followed only where the closure class and prototype method are statically exact; the Lua is never executed.

`resolved/unit-spell-semantics.tsv` is the stricter native-import view over that evidence. It labels every scripted spell `object-effect-ready`, `script-native-ready`, or `partial`, so a downstream importer can consume translated mechanics without treating unfinished state machines as complete. **37/37** rows are now implementation-ready: 17 are chiefly delivered by resolved WC3 effect objects and 20 have script-native parameters normalized directly. Examples include Faerie Dragon's actual `A0CG` **175** heal (rather than its 150 tooltip text), Dryad's 75 heal plus permanent +2 armor, Keeper's 150 heal/+3 armor followed by two 45-second Treants, Crusader/Paladin Inner Fire buffs, Paladin's +100 max HP and one-unit Resurrection path, Twin Smiley/Flamegunner mana-burn projectiles, Ancient Keeper's five-tree wall, Sandcloud periodic carriers, Mine Layer placement, multi-target Dragonhawk/Trapper casts, Ogre Lord's Berserk sequence, Mountain Giant's 350-area Taunt, and Brood Mother's delayed enabling of Web/Parasite autocast after Infest. Map-internal cross-checks prove `852066` as the `Ainf`/Inner Fire order, `852094` as Resurrection, `852126` as the `AOsf` summon family and `852100` as `Absk` Berserk; stable Warcraft order IDs additionally identify `852520` as `taunt`, `852212` as `webon`, and `852602` as `parasiteon`. Master of Elements is now fully normalized too: its shared protected Frost filter `SX` is statically resolved to generated predicate `vL`, which tests alive combat sapper + enemy of the subsystem owner.

Master of Elements uses five exact Elemental building-count buckets, exported independently in `script/element-building-buckets.tsv` and `resolved/element-building-buckets.tsv`: Fire = Altar of Fire/Blaze, Earth = Rock Pile/Greater Fissure, Lightning = the two lightning pillars, Water = the three fountains, and Wind = Trapped Gale/Monument of Wind Stream/Zephyros Memorial. Each cast rolls 0–99: below 50 launches Lightning, otherwise Frost. Lightning count is `2 + floor(lightning/3)`, split budget `2 + floor(wind/2)`, and damage `75 * min(1 + fire, 4)`; its custom projectiles move 20 units every 0.03 s, hit alive enemy combat sappers within 34, and split by ±30° according to the budget. Frost count is `5 + 2*water`, damage `75 * min(1 + earth, 4)`, and Frost Nova level `clamp(floor(wind/4), 1, 3)`; missiles spawn over a ±35° fan every 0.04 s, move 26 units every 0.03 s, collide within 38, deal direct cold damage, and cast `A043` Frost Nova on surviving victims. The protected Frost filter `SX` is now promoted as verified through static Wurst emission-order evidence: it resolves to `vL`, whose visible predicate is `isAliveCombatSapper(unit) and unit_isEnemyOf(unit,mIb)`.

Corpse/death content is explicit as well. Warcraft's unit `Death Type` is a two-bit capability value: `0` can't raise/no decay, `1` can raise/no decay, `2` can't raise/does decay, `3` can raise/does decay. Among the 167 authored production units the distribution is **38 / 2 / 24 / 103** respectively; the 162 normal-play subset is **38 / 2 / 24 / 98**. Mechanical classification cannot replace these bits: eleven mechanical production units are explicitly decay-only, for example Light Tank `h06T`. `resolved/production-unit-corpses.tsv` therefore preserves the actual capability bits and per-unit `Death Time` rather than inferring corpse behavior from biological/mechanical tags. `resolved/death-decay-constants.tsv` shows that this map leaves flesh decay at the Warcraft build default **2 s**, overrides bone decay **88 → 25 s**, and structure decay **30 → 0.1 s**. For decaying units the table also records the arithmetic death-time + flesh + bones; no-decay removal behavior is intentionally left uninterpreted rather than guessed.

Scripted building spells are now linked separately from object-editor ability attachment. `script/building-spell-registrations.tsv` recovers **15** exact generated registrations by joining the closure object's `BuildingSpellClosure_cast` prototype assignment to the protected building/ability registry call; `resolved/building-spells.tsv` then joins the effective ability fields and race metadata. A critical compatibility detail is that these buildings use mana as the long-form timer: all 15 owning buildings regenerate **1 mana/sec**, and each spell's protected mana cost equals its authored tooltip cadence (for example Skull Pile **12**, Death Pit **15**, Vessel of Purity **15**), while their ordinary WC3 ability cooldown fields are only **0 or 1 second**. The native importer should therefore use the explicit `cadence_seconds` field rather than interpreting WC3 ability cooldown as the Castle Fight building-spell period.

`resolved/building-spell-mechanics.tsv` goes one step further and covers **all 15/15** registrations with a normalized mechanic kind, target selector/predicate, script constants, linked rawcodes, concrete source functions and evidence classification. The resolver enriches linked ability/unit objects without pretending those object fields were proved by the Lua itself. Snowveil Fountain's automatic `SX` target filter is now statically resolved to `vL` (`alive-combat-sapper;enemy-of-mIb`). It also preserves exactly one detected evidence conflict rather than choosing a side: Chilling Mushroom's authored building ability text says **150 spell damage**, while the actually cast `A0AK` Storm Bolt object has `Damage=200`; both values and their provenance remain in the same mechanic row. The normalized rows also expose Frost Launcher's protected 50/100 chaos impact dummies and 10/12-second Freezing Breath effects, World Freezer's three-orb movement/target cycle and linked slow/freeze/damage abilities, the Orc totem/Serpent/Ceremonial effect objects, Death Pit's direct 50,000 death damage, Snowveil's 20% snow damage reduction plus 384-radius/350-damage manual detonation constants, and Thunderpaw's charged melee-triggered clamped universal splash formula.

The corpse-dependent building handlers are normalized one step further in `resolved/corpse-building-mechanics.tsv`. Skull Pile and Skull Shrine call `raiseFromCorpse`, which chooses a random **dying** combat sapper across the battlefield, excludes Undead units and units carrying `Avul` (Invulnerable), does **not** consult Warcraft's `Death Type.can_raise` bit, removes the selected unit/corpse, and spawns one of four exact unit rawcodes. The first outcome has **10%** probability and each of the remaining three has **30%**. Skull Pile therefore yields Skeletal Hero 10%, Skeleton Warrior 30%, Skeleton Archer 30%, Skeletal Mage 30%; Skull Shrine yields Skeletal General 10%, Greater Skeleton Warrior 30%, Greater Skeleton Archer 30%, Greater Skeletal Mage 30%. Vessel of Purity instead selects an already-**dead**, vulnerable, non-Undead combat sapper, consumes every qualifying corpse within **220** of that corpse, casts Far Sight at the location, and damages qualifying enemies within **300** for **150 universal damage**. This scripted eligibility is retained separately from ordinary WC3 corpse capability bits so the native engine does not accidentally conflate the two systems.

The building side is now similarly explicit. `ensureUnitObjectMetadataRegistered` creates **240** `UnitObjectMeta` rows that `CFBuilding_setup` consumes directly and `checkBuilding` validates against live catalog objects. The extractor recovers their gameplay arguments—spawned unit, gold/lumber/food, exact spawn interval, attack/defense indexes, and air/melee/mechanical/caster flags—and mirrors the generated numeric/boolean fingerprint (`517550`). Fifteen race initializer functions partition those same 240 buildings exactly, and `ensureUnitObjectUpgradeMetadataRegistered` contributes **90** authored upgrade edges. The race initializers independently express the same 90 edges through `CFBuilding_precursor`; extraction fails if those two sources disagree. They also recover the five income factors (`0.20`, `0.18`, `0.12`, `0.09`, `0.04`) plus explicit legendary-line, anti-air, siege, artillery, mode/AI, multi-target, cage-pressure, placement, spell/tower/power and tag wrappers. `resolved/production-buildings.tsv` joins those semantics to exact building footprints and derives the same `CFBuilding` income accumulation (`own = gold × factor / 100`, then add precursor income). Of 167 production definitions, **162 are normal-play rows and all 162 appear in `xO`**; the remaining five belong to the explicitly campaign-only Critter race (`X0Z0`). All 167 production definitions have WC3 object `build_time=2`; in Castle Fight this is the short building-construction/cancellation window, while `spawn_time` is the recurring production interval (for example Barracks is construction `2` seconds and Footman production `20` seconds). Non-production tower/totem definitions retain their own WC3 build-time values separately.

When compatibility conclusions are promoted into Castle Fight Native, record whether each value/behavior is directly verified from these files, inferred by cross-referencing several sources, observed in Warcraft III, or an intentional divergence. That matches the provenance policy in `docs/spec/40-content-data.md`.
